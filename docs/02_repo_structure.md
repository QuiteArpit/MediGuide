# Repository Structure and Folder Guide

## Layout

```
MediGuide/
├── README.md                     overview, safety statement, setup
├── requirements.txt              Python dependencies
├── .gitignore                    keeps large/secret files out of Git
├── docs/
│   ├── 01_project_charter.md
│   ├── 02_repo_structure.md
│   ├── 03_dataset_inventory.xlsx
│   ├── 04_symptom_questionnaire.xlsx
│   ├── 05_red_flag_rules.xlsx
│   ├── 06_heart_diet_rules.xlsx
│   └── 07_phase1_checklist.md
├── data/
│   ├── raw/                      original files, never edited
│   │   ├── DATA_SOURCES.md
│   │   ├── uci_heart/  ifct/  usda_fdc/  kaggle_symptoms/  open_food_facts/
│   └── processed/                cleaned outputs (reproducible from raw)
├── notebooks/                    01_data_inspection.ipynb, later EDA/modeling
├── src/
│   ├── data/                     loading, cleaning, food table building
│   ├── triage/                   questionnaire parsing, red-flag + rule engine
│   ├── models/                   risk model training and prediction
│   ├── diet/                     diet rules engine and food queries
│   └── app/                      API / UI (later)
├── tests/                        unit tests and scenario tests
└── reports/                      test scenarios, metrics, figures, final report material
```
Create the `src/` subfolders when you start using them (Git does not track empty folders; add a `.gitkeep` if needed).

## What belongs in each folder, and why

| Folder | What goes here | Why |
|---|---|---|
| `README.md` | Project summary, safety statement, setup, status | First thing evaluators and teammates read; keeps the safety wording visible |
| `docs/` | Charter, questionnaire, triage rules, diet rules, dataset inventory, decisions, meeting notes | Rules and decisions are as important as code in a medical-style project and must be reviewable by non-programmers (clinicians, faculty) |
| `data/raw/` | Original downloads exactly as received, plus `DATA_SOURCES.md` and checksums | Keeps a trustworthy original. Read-only means every result can be traced back and re-created |
| `data/processed/` | Cleaned, merged, feature-ready data generated by code | Separates original from derived data. If it is wrong, delete it and rebuild from raw |
| `notebooks/` | Exploration, inspection, charts, quick experiments (numbered: `01_...`, `02_...`) | Good for learning about the data. Not for final logic |
| `src/` | Reusable, tested code: cleaning functions, rule engine, model code, diet engine, app | Notebook logic that must be reused or tested moves here, so the app and tests use the same code |
| `tests/` | Unit tests; scenario tests that read `reports/phase1_test_scenarios.xlsx` | Safety needs automatic checks: e.g. every emergency scenario must return emergency advice, every time |
| `reports/` | Test scenarios, evaluation results, figures, final-report material | Keeps outputs separate from code and data; easy to hand to faculty |

## Working rules

1. **Never edit `data/raw/`.** Write cleaned data to `data/processed/`.
2. **Rules before models.** Safety rules in `src/triage/` run first; the model cannot override an emergency.
3. **No secrets in Git** (`kaggle.json`, API keys). Large raw files are not committed; the download steps are.
4. **Branches and reviews:** work on a branch (`feature/<name>`), open a Pull Request, and get one teammate's review before merging into `main`.
5. **Commit messages:** short and clear, e.g. `docs: add red-flag rules v0.1`.
6. **Naming:** numbered documents (`01_`, `02_`), lowercase with underscores for code, no spaces in file names.
7. **Medical content is versioned:** every change to a triage or diet rule is a commit with a reason; the clinician-review column in the rule sheets is updated.

## Quick setup commands

```bash
mkdir -p MediGuide/{docs,data/raw,data/processed,notebooks,src/{data,triage,models,diet,app},tests,reports}
cd MediGuide && git init
touch data/processed/.gitkeep notebooks/.gitkeep tests/.gitkeep reports/.gitkeep
```
